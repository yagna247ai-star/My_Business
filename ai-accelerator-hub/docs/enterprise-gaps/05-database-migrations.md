# 05 — Database and migrations

**Status:** production schema is live (70 tables), applied by hand. There is no migration history in git.

## Current state

- `packages/db/prisma/schema.prisma` now uses `provider = "postgresql"`. `prisma validate` and `prisma generate` pass, and the web build passes.
- Production: the initial schema was applied with `prisma db execute`, from `init_postgres.sql` generated by `prisma migrate diff --from-empty --to-schema-datamodel`. That file is in the session scratchpad, not in the repo, so it is not version-controlled. Table count verified: 70.
- `packages/db/prisma/migrations/` is **gitignored** and still holds the old SQLite migration lock (`migration_lock.toml` says `sqlite`). `prisma migrate deploy` fails with P3019 against Postgres.
- `apps/web/next.config.js` still contains a SQLite-only branch. It is harmless on Postgres.
- The local root `.env` still points `DATABASE_URL` at SQLite, so `npm run dev` will not match production until you run a local Postgres.
- `packages/db/prisma/*.db` files (dev and test SQLite databases) exist locally. They are gitignored.

## Gap

- No reproducible migration history. A future schema change cannot be deployed with `migrate deploy` until a fresh Postgres migration is created.
- No verified backup or restore. Neon offers point-in-time recovery, but it has not been tested.
- No migration is committed, so another developer cannot recreate the database from git.
- The `db:seed` and migration scripts still reference the SQLite workflow.

## Risk

- High operationally. A schema change is currently a manual `db execute` with no record in git.

## Decision needed

- Commit a fresh Postgres init migration (recommended), and confirm the backup policy: Neon PITR retention period, and whether to add scheduled `pg_dump` to S3 as `PENDING_CREDENTIALS.md` describes.

## Steps to close

1. Move the old `packages/db/prisma/migrations` folder aside (not deleted) and create a new one: `prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script` saved as `migrations/0001_init/migration.sql`, plus `migration_lock.toml` with `provider = "postgresql"`.
2. Mark the existing production schema as applied with `prisma migrate resolve --applied 0001_init`, so future migrations start from the current state.
3. Commit the migrations folder. Remove it from `.gitignore`.
4. Set Neon's retention to the required window. Run a restore into a branch and confirm the data comes back.
5. Remove the SQLite branch from `next.config.js` and point the root `.env` at a local Postgres (for example from `docker-compose.yml`).
